# Agent instructions

Primary reference for coding agents working in this repo.

- **Repo overview / packages**: [README.md](./README.md)

## Contribution rules

- **Secrets**: this repo deals with real credentials (`DAYTONA_API_KEY`, `GITHUB_CLIENT_SECRET`, `GITHUB_APP_*`, OAuth tokens generated by `packages/claude-credentials`). Read them from env vars only. Never hardcode a secret in source, never commit `.env`, `.env.local`, or `.env.test` (they're gitignored for a reason), and never `console.log`/print a token, API key, or credential object — including in error messages or debug output.
- **Keep the diff focused**: no unrequested refactors or reformatting of untouched files. Remove `console.log` debug statements, commented-out code, and stray TODOs before opening a PR.
- **Update docs in the same PR**: if you change documented behavior, update the matching doc — the relevant package's `README.md` (every package under `packages/*` has one), `DEVELOPMENT.md`, or `packages/sdk/TESTING.md`. `packages/sdk` is published to npm (see `publish:sdk` and `.github/workflows/npm-publish.yml`) — treat a change to its public exports (`packages/sdk/src/index.ts` and friends) as a breaking-change review, and update `packages/sdk/README.md` to match.
- **Prisma schema changes**: run `npm run prisma:validate` (schema syntax, no DB connection needed) and `npm run prisma:generate` after editing `prisma/schema.prisma`, and see [Database migration](./packages/web/README.md#database-migration). Never hand-edit a migration file that's already been applied — generate a new one with `npm run prisma:migrate`.

## What the user has to provide

The agent can follow the setup and workflow instructions in this repo on its own. The user provides values for these env vars by exporting them in the current shell environment.

> **Note for agents:** check whether these env vars are set by running the `env` command (e.g. `env | grep DAYTONA_API_KEY`). Do not assume they are unset — they are exported in the shell, not stored in a tracked file.

**Required for dev server and tests**

- `DAYTONA_API_KEY` — exported in the shell (reused by `.env.test`).

**Required for dev server**

- Auth: `GITHUB_CLIENT_ID` + `GITHUB_CLIENT_SECRET` (GitHub OAuth app).

**Optional** (only if those integrations are in scope)

- `SMITHERY_*` — remote MCP servers from the Smithery registry.
- `GITHUB_APP_*` — authenticated GitHub MCP server.

Before running tests or a dev server, confirm the required env vars above are exported, then follow [DEVELOPMENT.md](./DEVELOPMENT.md).

## Code style

This is a TypeScript monorepo (Next.js, Electron, Prisma) — there is no ESLint config in the repo today, so the conventions below are enforced by review, not CI. Don't add a Python-style convention (e.g. one-class-per-file, no-lambdas, no-comprehensions) — this codebase is function/hook-based, not OOP, and idiomatically uses `.map`/`.filter`/`.reduce`.

- **Types**: `tsconfig.json` has `"strict": true`. Don't introduce `any` or `as any` — it's rare in this codebase today (a handful of hits repo-wide) and should stay that way.
- **Naming**: camelCase for functions/variables/parameters, PascalCase for components/types/classes, UPPER_CASE for module-level constants (e.g. `INTERACTIVE_HARD_TIMEOUT_MINUTES` in `packages/web/lib/agent-run-limits.ts`).
- **Catch narrowly**: a caught value is `unknown`, not `Error`. Narrow with `error instanceof Error` before reading `.message` (the dominant pattern already, e.g. `packages/desktop/src/git-sync.ts`).
- **Never fail silently**: if a `catch` swallows an error instead of rethrowing, log it (`console.error`/`console.warn`) with enough context to act on, and add a comment explaining why it's safe to continue — see `packages/web/lib/agent-session.ts` ("MCP setup is best-effort — a failure here shouldn't block the turn") for the pattern to follow.
- **Logging**: this repo uses `console.*`, not a logging library. Prefix messages with the module name in brackets (e.g. `[dev-servers]`, `[sandbox]`) to match the existing convention.
- **Env vars**: `process.env.FOO` is read directly throughout the codebase (there's no centralized/validated config module). Follow the existing pattern rather than inventing a new one in a single file.

## Testing

- **Unit tests**: [Vitest](https://vitest.dev). Some packages colocate `*.test.ts` next to the source file (`packages/web/lib/*.test.ts`), others use a `tests/` directory (`packages/sdk/tests/`, `packages/sandbox-git/tests/`, `packages/sandbox-jobs/tests/`). Match whichever convention the package you're editing already uses.
- **Integration tests**: name them `*.integration.test.ts` or put them under a `tests/integration/` directory (see `packages/sandbox-terminal/tests/integration/`, run via that package's `test:e2e` script) to keep them separate from the fast unit suite.
- **End-to-end**: [Playwright](https://playwright.dev), under `packages/web/e2e/*.spec.ts`. Run with `npm run test:e2e -w @background-agents/web` — needs the test DB and env from [Testing](./packages/web/README.md#testing); see [DEVELOPMENT.md](./DEVELOPMENT.md#run-e2e-tests).
- **Run the unit suite before opening a PR**: `npm run prisma:generate && npm test` from the repo root runs `test` in every package that defines one (currently `sandbox-git`, `sandbox-jobs`, `sandbox-terminal`, `sdk`, `web`). There's no single root command for Playwright — run `test:e2e` in `packages/web` separately when your change touches that package.

## After editing code

Before running typecheck for the first time (or after pulling new changes), ensure dependencies are installed:

```bash
npm install
npm run prisma:generate
```

Then run `npm run typecheck` to verify there are no type errors. This is much faster than a full build (~5 seconds vs 2-3 minutes).

## Debugging

- Investigate with console logs.
- Prefer integration and end-to-end tests over narrow unit tests.
- Write a test that reproduces the bug before fixing it.
- After fixing, keep only the general-case tests — drop the one written to pin down this specific bug.

## Checks before opening a PR

```bash
npm install
npm run prisma:generate
npm run typecheck
npm test
```

- Changed `prisma/schema.prisma`? Also run `npm run prisma:validate`.
- Changed anything under `packages/web`? Also run `npm run test:e2e -w @background-agents/web` (see [DEVELOPMENT.md](./DEVELOPMENT.md#run-e2e-tests) for the test DB setup).
- Changed `packages/sdk`'s public API? Update `packages/sdk/README.md` in the same PR (see Contribution rules above).
